textmate_grammar.engine.oniglib¶

Port of vscode-textmate’s src/onigLib.ts — the oniguruma library adapter.

vscode-textmate drives tokenization through an injectable IOnigLib that provides

scanners and strings. Upstream this is backed by vscode-oniguruma (a wasm build of

oniguruma ~6.9). Here the same surface is provided on top of onigurumacffi, an ffi binding of oniguruma 6.9 — the same engine family, so the semantics carry over:

  • Pattern selection (leftmost match wins, ties resolved by the lowest pattern index) is done by oniguruma’s RegSet API (onig_regset_search with ONIG_REGSET_POSITION_LEAD), which is exactly the strategy vscode-oniguruma’s C++ findNextOnigScannerMatch uses for short strings.

  • The critical semantic (see the parity plan): \G matches exactly at the start offset of the scan, i.e. at the start_position passed to each OnigScanner.find_next_match_sync() call, not at a stored anchor. oniguruma binds \G to the search start, and vscode-textmate passes the token offset per call — Pattern.search(content, start=start_position) reproduces this 1:1. A pattern compiled once therefore matches at different offsets for different start_position values.

Capture indices are returned in Python code-point offsets (consistent with the rest of the Python port; upstream returns UTF-16 offsets, having decoded the UTF-8 wasm buffer). Unmatched capture groups — which oniguruma reports with offsets of -1 — are mapped to start == end == 0, the same clamp vscode-oniguruma applies when its convertUtf8OffsetToUtf16 encounters values below zero.

Every non-obvious piece references the ported section of vscode-oniguruma / onigLib.ts.

class textmate_grammar.engine.oniglib.OnigScanner(sources: collections.abc.Sequence[str])[source]¶

Port of OnigScanner from vscode-oniguruma — the scanner behind IOnigLib.createOnigScanner (onigLib.ts:43-46).

Patterns are compiled eagerly at construction, like vscode-oniguruma does; an invalid pattern raises onigurumacffi.OnigError where upstream throws the oniguruma error message. Matching uses one RegSet search per call, whose ONIG_REGSET_POSITION_LEAD strategy yields the same candidate selection as vscode-oniguruma’s C++ findNextOnigScannerMatch: the match beginning at the smallest offset wins and ties break toward the lowest pattern index.

string may be a plain string or an OnigString, as upstream. start_position is the offset the scan starts at, which is where \G binds: a pattern containing \G is compiled once and still matches at whatever initial offset the caller passes.

find_best_match(position: int, line: str, has_anchor: bool = False, has_back_references: bool = False) → textmate_grammar.engine.oniglib.IOnigMatch | None[source]¶

Convenience mirroring the pre-4.0 IOnigScanner.findBestMatch(position, line, hasAnchor, hasBackReferences) surface named in the porting plan.

position is the scan offset, so a \G binds there: with has_anchor=True the patterns are scanned as-is, with has_anchor=False FindOption.NOT_BEGIN_POSITION makes every \G fail (the same equivalent option vscode-textmate’s getFindOptions builds for allowG=False in grammar/tokenizeString.ts:549-557).

has_back_references is bookkeeping parity for the old signature only: in the current vscode-textmate, \n backreference patterns are resolved before scanning (rule.ts resolveBackReferences, ported in textmate_grammar.engine.regexsource), so the scanner has nothing to do with them — the flag is accepted and unused.
